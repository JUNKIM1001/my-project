## 1. アーキテクチャ

```
   お出かけアプリ（利用者）
            │  HTTPS GET /v1/shrines?pref=京都府&city=宇治市
            ▼
   ┌─────────────────────────┐
   │ Vercel Edge Network      │  CDNキャッシュ（s-maxage=3600）
   │  └ 東京リージョン hnd1   │  ← ヒットすれば関数を起動せず即応答
   └─────────────────────────┘
            │ ミス時のみ
            ▼
   ┌─────────────────────────┐
   │ Vercel Function (Node)   │
   │  1. レート制限チェック    │→ Upstash Redis（IP単位・スライディングウィンドウ）
   │  2. パラメータ検証        │
   │  3. 地域解決／距離計算    │
   │  4. JSON整形              │
   │     ↑                    │
   │  同梱データ（ビルド時生成）│  api-data.json（メモリ上・DBアクセスなし）
   └─────────────────────────┘

   ［データ更新フロー・週1回］
   Supabase ──> build-data.mjs ──> api-data.json ──> Vercel再デプロイ
```

### 1.1 なぜデータを「同梱」するのか

リクエストごとにSupabaseへ問い合わせる案と比較して、同梱を選ぶ。

| 観点 | 同梱（採用） | 都度DB照会 |
|---|---|---|
| 応答速度 | メモリ内処理のみ（数ms） | DB往復が加わる（数十〜百ms） |
| コスト | ゼロ（無料APIで青天井の課金が起きない） | リクエスト数に比例。**乱用時に課金が膨らむ** |
| 障害耐性 | DB障害の影響を受けない | DB障害＝API停止 |
| セキュリティ | DBを外部に晒さない | 攻撃面が増える |
| 鮮度 | 再デプロイまで反映されない（週1回で十分） | 即時 |

**認証なしの公開APIでは「乱用されてもコストが増えない」ことが最重要**。
データは2,086件・数百KB（長文解説を除くため軽い）で、全件をメモリに載せても問題ない。

実測（Node 26 / 手元のMac）:

| 処理 | 実測値 |
|---|---|
| 2,086件の距離計算＋ソート | **0.29ms/回**（100回で29ms） |
| 座標を小数第2位に丸めた際の位置ずれ | 228m（仕様の「約1km以内」を満たす） |

したがって空間インデックス（PostGIS等）は不要で、素朴な全件走査で十分速い。

### 1.2 デプロイ先を分ける

おまいりナビWeb（`omairi-navi.vercel.app`）とは**別のVercelプロジェクト**にする。

- Webの改修でAPIが巻き添えデプロイされない（利用者への影響を切り離す）
- APIだけを独自ドメイン `api.omairi-navi.app` に割り当てられる
- 障害時にどちらが原因か切り分けやすい

## 3. データ供給

### 3.1 ビルド時変換 `scripts/build-data.mjs`

Supabase（またはローカルの `appdata.json`）から読み、**APIが返す形に絞った**JSONを生成する。

やること:
1. `long_description` を**落とす**（CC BY-SA のため配布しない ← 仕様 §1.3）
2. 神仏・ご利益を社寺ごとに解決して埋め込む（実行時のJOINをなくす）
3. 都道府県・市区町村の索引と件数を先に作る
4. `data_version` に生成日を入れる

```js
// 出力形（イメージ）
{
  "data_version": "2026-07-25",
  "shrines": [ { id, name, kana, type, sect, pref, city, address, lat, lng,
                 summary, deities:[{id,name,kind}], goriyaku:[{id,name}],
                 nt, goshuin, tv, website, source, image } ],
  "goriyaku": [ { id, name, count } ],
  "areas": { "京都府": { count: 121, cities: { "宇治市": 8, ... } } },
  "counts": { shrines: 2086, deities: 481, ... }
}
```

### 3.2 実行時の索引 `lib/data.js`

関数のコールドスタート時に1回だけ構築し、以降のリクエストで使い回す
（Vercel Functionsはインスタンスが再利用されるため実質キャッシュになる）。

```js
byId        : Map<string, Shrine>
byPref      : Map<string, Shrine[]>
byPrefCity  : Map<"京都府|宇治市", Shrine[]>
cityNames   : Map<pref, string[]>   // 前方一致・部分一致の探索用
```

## 4. 地域名の解決 `lib/area.js`

仕様 §3.1 の実装。逆ジオコーディングの表記ゆれを吸収する。

```
normalizePref(input):
  全角/半角・空白を正規化
  完全一致 → そのまま
  接尾辞なし（"京都"）→ "京都府" を探す（都/道/府/県 を順に補って照合）
  見つからなければ null → 400

resolveCity(pref, input):
  1. prefix   : input で始まるものを集める（完全一致もここに含まれる）
                すべて input と等しい → match="exact"
                区などを含む         → match="prefix"
  2. contains : 1が0件のとき input を含むもの（"美郷町" → "仙北郡美郷町"）
  3. 見つからず: pref_only（都道府県全体を返し meta.notice で通知）
```

**設計判断1: 完全一致より前方一致を先に置く（実データ検証で判明）**

データには政令市の「市名のみ」と「市名＋区」が混在する。実測値:

| 入力 | 完全一致のみ | 前方一致 |
|---|---|---|
| `京都市` | 81件 | **102件**（各区を含む） |

混在は12政令市（札幌・仙台・さいたま・川崎・横浜※・名古屋・京都・大阪・堺・神戸・北九州・福岡・熊本）で発生。
完全一致を優先すると `京都市` の検索で21件を静かに取りこぼすため、**前方一致を第一段**とする。

**設計判断2: 市区町村が解決できなくてもエラーにしない**

お出かけアプリで「結果ゼロ」や「エラー画面」になるより、
広めの結果＋注記のほうが利用者・エンドユーザー双方に有益。

## 5. 位置情報の扱い `lib/geo.js`

プライバシー方針（仕様 §1.1）の実装。

```js
// 受け取った座標は必ず丸める。丸めた値だけを以降で使う。
const coarse = (v) => Math.round(v * 100) / 100;   // 小数第2位 ≒ 1.1km
```

- **アクセスログに `lat`/`lng` を出力しない**（クエリ文字列ごとログしない設定にする）。
- 丸めた座標も保存しない。メモリ上で距離計算に使うのみ。
- Vercelのログ設定で、リクエストURLのクエリを記録しないようにする。
- 距離はHaversine（半径6,371km）。

## 6. レート制限 `lib/ratelimit.js`

- **Upstash Redis**（無料枠）のスライディングウィンドウ。IPをキーにする。
- IPは `x-forwarded-for` の先頭を採用。
- **失敗時はフェイルオープン**（Redis障害時は制限せず通す）。
  公開APIでは「止まる」より「一時的に緩い」ほうが害が小さい。
- IPは**ハッシュ化して**キーにする（生IPを保存しない）。

```
key = sha256(ip + salt)     // 生IPは残さない
1分窓: 60  /  1日窓: 10,000
```

- 全レスポンスに `RateLimit-*` ヘッダを付与、超過時は `429` + `Retry-After`。

## 7. キャッシュ

- CDN: `Cache-Control: public, s-maxage=3600, stale-while-revalidate=86400`
- `ETag` はレスポンス本文のハッシュ。`If-None-Match` 一致なら `304`。
- **CDNヒット時は関数が起動しない＝レート制限も消費しない**ため、
  同一クエリの繰り返しは実質無制限になる。これは意図した挙動。

## 8. エラー処理 `lib/problem.js`

RFC 9457 に沿ったJSONを返す。`type` は `https://api.omairi-navi.app/errors/{code}`。
利用者が機械的に分岐できるよう、`type` を安定させる（文言は変えてもURIは変えない）。

## 9. テスト方針

実装と同時に、以下の**振る舞いを固定するテスト**を書く。

| 対象 | 確認する内容 |
|---|---|
| 地域解決 | `京都`→`京都府` / **`京都市`→102件（区を含む・81件でないこと）** / `美郷町`→`仙北郡美郷町` / 未解決→`pref_only` |
| 座標の丸め | `34.8892` → `34.89`。第3位以下が結果に影響しないこと（丸め誤差は実測228m） |
| 距離 | 既知2地点の距離が実測値と一致（京都駅→平等院 = 12.0km） |
| 絞り込み | `goshuin=true` が88件、`tv=true` が「1年以内のみ」を返すこと |
| tvの経年 | 放映日が1年+1日前のデータは `tv: null` になること（時刻を固定して検証） |
| ライセンス | レスポンスに `long_description` 相当が**含まれない**こと |
| エラー | `lat` のみ指定→400、`radius_km=200`→400、未知ID→404 |

## 10. 段階リリース

| 段階 | 内容 | 判断ポイント |

| **1. 内部確認** | Vercelのプレビュー環境に配備し、実データで応答を確認 | 仕様どおりか・速度 |

### 運用
- データ更新は週1回（既存の週次クロールに合わせる）→ 自動で再ビルド・再デプロイ。
- `/v1/meta` の `data_version` で利用者が鮮度を確認できる。
- 障害・仕様変更は changelog に記録し、破壊的変更は `/v2` を新設（仕様 §9）。
